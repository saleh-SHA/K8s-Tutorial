Chapter 10

Scaling your application

Three kinds of scaling, one control loop.

Manual scaling

Manual scaling is changing the replica count with kubectl scale or by editing the Deployment.

Horizontal Pod Autoscaling

The Horizontal Pod Autoscaler automatically adjusts replica counts based on metrics. To use it you need the metrics-server installed in the cluster (which is included in most managed services and in minikube via minikube addons enable metrics-server).

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

This says: keep CPU averaged across all pods at around 70 percent of their CPU requests, scaling between 3 and 20 replicas as needed. You can also scale on memory or on custom application metrics through an adapter like Prometheus Adapter or KEDA.

Vertical and cluster autoscaling

Vertical Pod Autoscaling adjusts the CPU and memory requests of pods rather than the count. It is less commonly used directly because it requires restarting pods to apply changes, but it is useful for right-sizing in "recommendation only" mode.

Cluster Autoscaling adds or removes nodes from the cluster itself, useful in cloud environments where new VMs can be provisioned on demand. On a fixed-size deployment server this does not apply.

Event-driven autoscaling with KEDA

CPU-based HPA answers "are my pods busy?" But many workloads should scale on something the CPU does not reflect — a queue that is backing up, a stream with a growing lag, a burst of incoming jobs. A worker consuming a Kafka topic might sit at low CPU while ten thousand messages pile up behind it. KEDA (Kubernetes Event-Driven Autoscaling) closes that gap.

KEDA scales a Deployment based on external event sources — Kafka topic lag, RabbitMQ queue depth, AWS SQS message count, Azure Service Bus, and dozens more. Crucially, it can scale to zero when there is no work, then spin pods up the moment events arrive, which CPU-based HPA cannot do. It works by driving an HPA under the hood, so you keep the familiar mechanics and just add event awareness.

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-worker
  namespace: shop
spec:
  scaleTargetRef:
    name: order-worker          # the Deployment to scale
  minReplicaCount: 0            # scale to zero when idle
  maxReplicaCount: 30
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka.shop.svc:9092
      consumerGroup: orders
      topic: orders
      lagThreshold: "100"        # +1 replica per 100 messages of lag

Rule of thumb for choosing: scale on CPU/memory with HPA when load tracks request volume (the shop's web frontend); scale on events with KEDA when work arrives as queued messages or jobs and you want to scale to zero between bursts (a background order-processing worker). They are complementary, and many clusters run both for different workloads.

Rule of thumb

Prefer scaling out (more replicas) to scaling up (bigger pods). Many small pods are more resilient to node failures than a few big ones. Always set both requests and limits, and base your requests on actual observed usage rather than guesses.
