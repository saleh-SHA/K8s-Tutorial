Chapter 08

Configuration & secrets

Separate the values from the code, every time.

Why decouple configuration

Hard-coding configuration into container images is an anti-pattern. ConfigMaps and Secrets are the standard way to inject values at runtime, letting the same image deploy to staging and production with different settings.

ConfigMaps

A ConfigMap holds non-sensitive key-value data:

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  DATABASE_HOST: "postgres.default.svc.cluster.local"
  FEATURE_FLAGS: "new_ui=true,beta=false"

Secrets

A Secret holds sensitive data. Using stringData lets you write plain text; Kubernetes handles the encoding:

apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
type: Opaque
stringData:
  DATABASE_PASSWORD: "s3cret-p@ssw0rd"
  API_KEY: "abc123xyz"
Important

Secrets are base64-encoded, not encrypted. They are only encrypted at rest if you have configured etcd encryption, which you should. The base64 is for transport, not security.

Mounting into a pod

spec:
  containers:
  - name: app
    image: myapp:1.0
    envFrom:
    - configMapRef:
        name: app-config
    - secretRef:
        name: app-secrets

Secrets in git

Never commit Secrets to git as-is. Use one of the following: Sealed Secrets, which encrypts secrets that can be safely committed and decrypted only inside the cluster; External Secrets Operator, which pulls from systems like AWS Secrets Manager, HashiCorp Vault, or GCP Secret Manager; or SOPS with age or KMS encryption. Pick one early and stick with it.

External secret managers

Kubernetes Secrets are fine for many teams, but at scale most organisations keep the source of truth in a dedicated secret manager and sync it into the cluster. The managers — HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, Google Secret Manager — give you centralised auditing, fine-grained access policies, automatic rotation, and one place to revoke a leaked credential across every cluster at once.

The usual bridge is the External Secrets Operator: you commit a non-sensitive ExternalSecret manifest to git that references a secret by name, and the operator fetches the real value from the manager and materialises a normal Kubernetes Secret. The shop's database password lives in Vault; git only ever contains the pointer.

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: postgres-secrets
  namespace: shop
spec:
  refreshInterval: 1h          # re-pull (picks up rotations)
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: postgres-secrets     # the K8s Secret it creates
  data:
  - secretKey: POSTGRES_PASSWORD
    remoteRef:
      key: shop/postgres
      property: password

Rotation

A secret that never changes is a secret that, once leaked, is compromised forever. Rotation means regularly replacing credentials so a stolen one stops working. With an external manager this is largely automatic: the manager issues a new value (Vault can even generate short-lived, dynamic database credentials on demand), the External Secrets Operator re-pulls on its refresh interval, and a rolling restart picks up the new value. The key practice is to make rotation routine and boring rather than a panicked response to a breach — and to ensure your application can pick up a changed secret without a manual redeploy.

How secrets leak — and how to avoid it

Most secret exposure is mundane, not sophisticated. The recurring culprits: committing a secret to git (it lives forever in history even after deletion — add a pre-commit scanner like gitleaks), baking secrets into container images (anyone who can pull the image can read them — use a .dockerignore and never COPY a .env), logging secret values (scrub them from application logs and error reports), over-broad RBAC (anyone who can read Secrets in a namespace can read all of them — scope access tightly), and unencrypted etcd (Secrets are only base64-encoded at rest unless you enable etcd encryption, covered in the security chapter). None of these require an attacker to be clever; they just require you to be careless once.
