Chapter 09

Persistent storage

Containers forget; PersistentVolumes remember.

The storage model

Containers are stateless by default. Anything written to a container's filesystem is lost when the container restarts. For databases, uploaded files, and other stateful data, you need persistent storage.

The Kubernetes storage model has three concepts. A StorageClass describes a type of storage available in the cluster, such as fast SSDs or cheap spinning disks. A PersistentVolumeClaim is your application's request for some storage of a particular size and class. A PersistentVolume is the actual chunk of storage that gets bound to the claim, often provisioned dynamically when the claim is created.

Requesting storage

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: local-path

Mounting it into a pod

spec:
  containers:
  - name: db
    image: postgres:17
    volumeMounts:
    - name: data
      mountPath: /var/lib/postgresql/data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data

StatefulSets for clustered state

For stateful applications that need stable network identities (the pod always called db-0, the pod always called db-1) and individual persistent volumes per pod, use a StatefulSet instead of a Deployment. StatefulSets are the right tool for databases, message queues, and other stateful clustered software.

A word of caution

For production, you should strongly consider using a managed database service rather than running databases in Kubernetes yourself. The operational burden of running Postgres or MySQL well inside Kubernetes is significant.

Access modes

ReadWriteOnce means the volume can be mounted by one node at a time. ReadWriteMany allows multiple nodes to mount simultaneously and is needed for shared file storage, but it requires a storage backend that supports it (NFS, CephFS, or a cloud filesystem service). ReadOnlyMany is for read-only sharing.

A storage decision matrix

Choosing where state should live is one of the highest-stakes decisions in a cluster. This matrix maps common needs to the right answer.

What you haveUseWhy
Scratch space, lost on restartemptyDirFast, ephemeral, tied to the pod's lifetime
Single-pod persistent dataPVC, ReadWriteOnceSurvives restarts; one node at a time
Shared files across many podsPVC, ReadWriteMany (NFS/CephFS/cloud FS)Concurrent multi-node access

Self-hosted vs managed databases

You can run PostgreSQL in Kubernetes — the shop example does, for teaching. But running a database well in production (replication, failover, point-in-time recovery, version upgrades, performance tuning) is a specialist job. For most teams a managed database (Amazon RDS, Google Cloud SQL, Azure Database) is the better default: the provider handles the hard operational parts, and your cluster connects to it as an external endpoint via an ExternalName Service or plain connection string. Run databases in-cluster when you have a deliberate reason (cost, data residency, an operator like CloudNativePG that automates the hard parts) — not by accident because everything else is in Kubernetes.

Backup and disaster recovery

Persistent volumes are not backups. A deleted namespace, a corrupted database, or a failed upgrade can destroy data that lives only on a PVC. A real recovery story has three parts: cluster-object backup, volume snapshots, and — the part everyone skips — tested restores.

Velero is the standard tool for backing up Kubernetes itself: it captures cluster resources (your manifests, as they actually exist) and can trigger volume snapshots through the CSI driver, storing everything in object storage like S3. Scheduled backups are one command:

# back up the shop namespace, including its volumes, every night, keep 30 days
velero schedule create shop-nightly \
  --schedule="0 1 * * *" \
  --include-namespaces shop \
  --ttl 720h

# restore from the most recent backup
velero restore create --from-schedule shop-nightly

CSI volume snapshots capture point-in-time copies of a volume's data, which Velero can orchestrate or you can take directly with a VolumeSnapshot object. But a backup you have never restored is a hope, not a plan: schedule a periodic restore drill into a scratch namespace and confirm the data actually comes back. The first time you test a restore should never be during a real outage.

Storage trade-offs in the cloud

Block storage (cloud disks, ReadWriteOnce) is fast and cheap but attaches to one node — ideal for databases. Shared filesystems (ReadWriteMany) are convenient for multi-pod access but slower and pricier. Object storage (S3-style) is cheapest and infinitely scalable but is not a filesystem — applications must speak its API. Match the storage class to the access pattern rather than reaching for shared storage by default.
