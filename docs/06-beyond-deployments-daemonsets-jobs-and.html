Chapter 06

Beyond Deployments: DaemonSets, Jobs & CronJobs

A Deployment is for long-running, identical replicas. Three other controllers cover the cases it does not.

Deployments assume your workload is a fleet of interchangeable, always-on replicas — perfect for the shop's stateless frontend and API. But three common shapes do not fit that mould: something that must run once per node, something that runs to completion and stops, and something that runs on a schedule. Kubernetes has a purpose-built controller for each.

DaemonSets — one pod per node

A DaemonSet ensures a copy of a pod runs on every node (or every node matching a selector). As nodes join the cluster, they automatically get the pod; as they leave, the pod is cleaned up. This is the right tool for node-level agents — things that need to see what is happening on each machine.

Typical DaemonSet workloads: Fluent Bit or Vector collecting logs from every node, Node Exporter exposing per-node hardware and OS metrics to Prometheus, Falco watching kernel syscalls for runtime security threats, and Cilium or other CNI agents that must run everywhere to wire up pod networking. You rarely write these yourself — they ship as DaemonSets in their Helm charts — but recognising the pattern explains why they appear on every node.

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluent-bit
  namespace: logging
spec:
  selector:
    matchLabels:
      app: fluent-bit
  template:
    metadata:
      labels:
        app: fluent-bit
    spec:
      tolerations:                 # also run on control-plane nodes
      - operator: Exists
      containers:
      - name: fluent-bit
        image: fluent/fluent-bit:3.1
        resources:
          requests: { cpu: 50m, memory: 64Mi }
          limits:   { cpu: 200m, memory: 128Mi }
        volumeMounts:
        - name: varlog
          mountPath: /var/log
          readOnly: true
      volumes:
      - name: varlog
        hostPath: { path: /var/log }   # read the node's logs

Jobs — run once to completion

A Job runs one or more pods until a specified number of them complete successfully, then stops. Unlike a Deployment, a Job is done when its work is done — it does not restart finished pods. Use Jobs for one-off batch work: a database migration before a release, a data import, a one-time report, a cache warm-up.

apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  namespace: shop
spec:
  backoffLimit: 4            # retry a failing pod up to 4 times
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: migrate
        image: ghcr.io/example/shop-api:1.0.0
        command: ["alembic", "upgrade", "head"]
        envFrom:
        - secretRef:
            name: postgres-secrets

Run it and watch it finish: kubectl apply -f migrate-job.yaml then kubectl get jobs -n shop. The pod moves to Completed, not Running. For parallel batch work, set completions (how many successes you need) and parallelism (how many run at once).

CronJobs — Jobs on a schedule

A CronJob creates a Job on a cron schedule. This is the native way to run periodic tasks — nightly database backups, hourly report generation, regular cleanup of stale data — without standing up a separate scheduler.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
  namespace: shop
spec:
  schedule: "0 2 * * *"          # 02:00 every day
  concurrencyPolicy: Forbid       # don't start a run if the last is still going
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: backup
            image: postgres:17
            command: ["/bin/sh", "-c"]
            args:
            - pg_dump -h postgres -U shop shop | gzip > /backup/shop-$(date +%F).sql.gz
            envFrom:
            - secretRef:
                name: postgres-secrets
            volumeMounts:
            - name: backup
              mountPath: /backup
          volumes:
          - name: backup
            persistentVolumeClaim:
              claimName: backups
Choosing the right controller

Long-running, scalable, identical replicas → Deployment. Stable identity and per-pod storage (databases, queues) → StatefulSet (storage chapter). One per node → DaemonSet. Runs once and stops → Job. Runs on a schedule → CronJob. Picking the wrong one is a common early mistake — a database in a Deployment, or a backup script in a Deployment that "finishes" and gets restarted forever.
