Chapter 16

Production checklist & maturity model

Before real users — find your level, then climb.

Production-readiness is not a single bar you clear; it is a ladder you climb. The four levels below let you locate where you are and see what the next rung requires. Be honest about your current level — most teams overestimate — and treat the gap to the next level as your roadmap.

LevelYou have…The risk you still carry
1 · BeginnerWorkloads deployed; Services and Ingress working; basic kubectl fluencyNo resource limits, no probes, single replicas — a node failure or a memory leak takes you down
2 · IntermediateRequests/limits everywhere; liveness/readiness probes; multiple replicas; rolling updates; centralised logs and metricsManual deploys, ad-hoc secrets, no policy enforcement, untested backups
3 · AdvancedGitOps; NetworkPolicies (default-deny); Pod Security enforced; PDBs and topology spread; HPA/KEDA; tested backups; defined SLOs and alertingSupply-chain gaps, partial DR testing, reliability not yet budget-driven
4 · ExpertSigned images verified at admission (Kyverno/OPA); SBOMs; error-budget-driven release decisions; multi-zone HA; regular restore and failover drills; distributed tracingDiminishing returns — now it is about cost, scale, and organisational maturity

The detailed checklist below is the reference for what "done" means in each category. Levels 1–2 should satisfy the Infrastructure, Workloads, and Reliability items; level 3 adds Security and Observability; level 4 hardens Operations and supply chain.

Infrastructure

Cluster runs a supported Kubernetes version. Worker nodes have enough headroom that no single node failure causes an outage. etcd is backed up regularly and restoration has been tested. Logs and metrics are shipped to a central place outside the cluster.

Workloads

Every Deployment has resource requests and limits. Every workload has appropriate liveness and readiness probes. Critical workloads have PodDisruptionBudgets. Horizontal Pod Autoscalers are configured where load varies. Images are pinned by digest or signed.

Security

Pod Security Standards are enforced on every namespace. Containers run as non-root with read-only filesystems and dropped capabilities. NetworkPolicies implement default-deny. RBAC follows least privilege; the default service account is not used by applications. Secrets are encrypted at rest. Image scanning happens in CI. Kubernetes and node OS receive security updates promptly. The Ingress or Gateway controller is one that is still actively maintained — notably, the community ingress-nginx is retired and should be migrated off.

Reliability

Updates use rolling deployments with appropriate surge and unavailable settings. Rollbacks have been tested. Multiple replicas exist for any user-facing service. Persistent data is backed up and restoration has been tested. There is a runbook for common failures.

Observability

Centralized logging captures all container output. Metrics dashboards exist for cluster health and per-application performance. Alerts fire on meaningful conditions (high error rate, pod restart loops, low free disk, certificate expiry) rather than on noise. A way to trace requests across services exists if you have more than one service.

Operations

Manifests are stored in version control. Changes go through code review before reaching production. A GitOps tool such as Argo CD or Flux applies changes from git to the cluster, so the cluster's actual state matches the committed state by construction. Deployments are reproducible from scratch.
