Chapter 12

Security hardening

Layered defense, starting with the highest-impact wins.

Run as non-root

Add a securityContext to your pods:

spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: myapp:1.0
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop:
        - ALL

This combination is sometimes called the "restricted" Pod Security Standard. If your container image cannot run with these constraints, fix the image rather than loosen the constraints.

Pod Security Admission

Enforce these standards namespace-wide:

kubectl label namespace production \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted

NetworkPolicies for zero trust

By default, every pod can talk to every other pod in the cluster. NetworkPolicies let you implement zero-trust networking.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: traefik
    ports:
    - protocol: TCP
      port: 80
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: postgres
    ports:
    - protocol: TCP
      port: 5432
  - ports:
    - protocol: UDP
      port: 53

NetworkPolicies require a CNI plugin that enforces them — Calico and Cilium are the common production choices, and most managed clusters enable enforcement by default. (Note that not every CNI enforces policies: if you write a policy and nothing changes, confirm your CNI actually supports enforcement.) For self-hosted clusters, Cilium is the most widely adopted option and brings eBPF-based performance and observability alongside policy enforcement.

RBAC with least privilege

A Role describes what actions are allowed within a namespace; a RoleBinding ties that Role to a user or service account. Avoid using the default service account for application pods.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: web
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: web
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: web
subjects:
- kind: ServiceAccount
  name: web
roleRef:
  kind: Role
  name: web
  apiGroup: rbac.authorization.k8s.io

Software supply-chain security

An attacker does not need to breach your cluster if they can compromise something you deploy into it — a base image, a dependency, the build pipeline itself. Supply-chain security is about trusting what you run, end to end.

Three practices form the core. First, scan images for known vulnerabilities before they ship — Trivy, Grype, and Snyk all do this and slot into CI as a gate (recall the Trivy step in the CI pipeline). Second, generate a Software Bill of Materials (SBOM) — a machine-readable inventory of every component and version in an image — so that when the next widespread vulnerability lands, you can answer "are we affected?" in minutes instead of days. Third, sign your images with Cosign (part of the Sigstore project) so the cluster can cryptographically verify that an image was built by your pipeline and not substituted or tampered with.

# sign an image (keyless, via Sigstore's transparency log)
cosign sign ghcr.io/example/shop-api@sha256:<digest>

# verify before trusting it
cosign verify ghcr.io/example/shop-api@sha256:<digest> \
  --certificate-identity-regexp '.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

Verification only protects you if it is enforced — which is what policy engines and admission control are for.

Admission control and policy enforcement

An admission controller intercepts every object on its way into the cluster, after authentication and authorisation but before it is persisted, and can validate or mutate it. This is the enforcement point for organisation-wide rules: reject unsigned images, require resource limits, forbid :latest tags, mandate that every pod has a non-root securityContext.

Two policy engines dominate. Kyverno writes policies as Kubernetes YAML (no new language to learn) and is the easier on-ramp for most teams. OPA Gatekeeper uses the Rego policy language and is more powerful for complex logic. A Kyverno policy that blocks unsigned shop images:

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-signed-images
spec:
  validationFailureAction: Enforce      # reject violations (vs Audit)
  rules:
  - name: verify-shop-signature
    match:
      any:
      - resources:
          kinds: [Pod]
    verifyImages:
    - imageReferences: ["ghcr.io/example/*"]
      attestors:
      - entries:
        - keyless:
            issuer: https://token.actions.githubusercontent.com

With this in place, a pod referencing an unsigned or tampered image is rejected at admission — it never schedules. The same engine enforces the Pod Security Standards, resource-limit requirements, and naming conventions, giving you a single, auditable place where "what is allowed to run here" is defined as code.

Other essentials

Pin by digest (myapp@sha256:abc123...) so a tag re-push cannot silently change what runs. Encrypt etcd at rest — by default it stores secrets in plaintext on disk. Enable audit logging on the API server so you have a record of who did what. Keep Kubernetes itself up to date — the project supports only the three most recent minor versions. Use a maintained ingress/gateway controller — recall that the community ingress-nginx is retired.
