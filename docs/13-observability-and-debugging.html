Chapter 13

Observability & debugging

Set things up before the fire, not during it.

The three pillars, and how they fit together

Observability rests on three kinds of data, and the skill is knowing which one answers which question. Metrics are cheap numeric time-series — they tell you that something is wrong (error rate spiked, latency climbed). Logs are detailed event records — they tell you what happened in a specific component. Traces follow a single request across multiple services — they tell you where in a distributed call chain the time or the failure went.

A typical investigation uses all three in sequence: a metrics dashboard alerts that the shop's API p99 latency tripled; a trace of a slow request shows the time is spent in the call to Postgres; the database pod's logs reveal a slow query or a lock. Metrics found the problem, traces localised it, logs explained it. Tools that correlate the three (jump from a metric spike to the matching traces to the underlying logs) turn a multi-tool scavenger hunt into a few clicks.

Metrics — Prometheus, Grafana, Alertmanager

The de-facto metrics stack is Prometheus (scrapes and stores time-series), Grafana (dashboards), and Alertmanager (routes alerts to email, Slack, PagerDuty). All three install together from one Helm chart:

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install monitoring prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace

This ships with dashboards for cluster and node health out of the box. Instrument your own applications to expose Prometheus metrics on a /metrics endpoint — most frameworks have a one-line plugin — and Prometheus will scrape them automatically. Alert on the golden signals from the reliability chapter (high error rate, p99 latency over your SLO, pod restart loops, certificate expiry) rather than on noise.

Logs — Fluent Bit to Loki or Elasticsearch

Kubernetes captures every container's stdout and stderr. For a few pods, kubectl logs is enough:

kubectl logs <pod-name>
kubectl logs <pod-name> -c <container-name>  # multi-container pods
kubectl logs <pod-name> --previous            # the previous instance after a crash
kubectl logs -f <pod-name>                    # follow live
kubectl logs -l app=web --tail=100            # across all pods matching a label

At any real scale, ship logs to a central store before pods (and their logs) disappear. The common pattern is a Fluent Bit (or Vector) DaemonSet — recall the DaemonSet chapter — collecting from every node and forwarding to Loki (lightweight, integrates tightly with Grafana) or Elasticsearch (heavier, powerful full-text search), or a cloud logging service. Centralised logs survive the pod that produced them, which is exactly when you need them most.

Traces — OpenTelemetry, Jaeger, Tempo

For anything beyond a single service, distributed tracing is what makes latency debuggable. OpenTelemetry is the vendor-neutral standard for instrumenting code and emitting traces; the OpenTelemetry Collector runs in the cluster, receives traces from your apps, and forwards them to a backend like Jaeger or Tempo. A single trace shows the shop request fanning out — frontend → API → Redis → Postgres — with timing for each hop, so a slow dependency is obvious at a glance rather than inferred from scattered logs.

Essential debugging commands

For day-to-day inspection (the dedicated troubleshooting chapter goes deeper on specific failures):

kubectl get events --sort-by=.metadata.creationTimestamp
kubectl describe pod <name>
kubectl exec -it <pod-name> -- /bin/sh
kubectl port-forward <pod-name> 8080:8080
kubectl debug <pod-name> -it --image=busybox --target=<container>

The kubectl debug command creates an ephemeral debug container alongside a running pod, invaluable when your production image is a minimal distroless image with no shell.
