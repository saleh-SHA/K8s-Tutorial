Chapter 14

GitOps & CI/CD

Stop running kubectl apply by hand. Let git be the source of truth.

So far every change has been applied with kubectl apply from a laptop. That works for learning, but in production it means cluster state lives in whoever's terminal last touched it, with no audit trail and no easy rollback. GitOps fixes this by making a git repository the single source of truth: you change YAML in git, and an in-cluster agent continuously reconciles the live cluster to match. The cluster's state is, by construction, whatever git says it should be.

The pipeline, end to end

The full path from a code change to a running update splits cleanly into two halves: CI (continuous integration) builds and verifies an artifact, and CD via GitOps deploys it. The boundary between them is the registry and the config repo.

The CI half

Continuous integration takes a commit and produces a verified, pushed image. A minimal GitHub Actions workflow for the shop API:

name: ci
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
    - uses: actions/checkout@v4
    - name: Log in to GHCR
      run: echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
    - name: Build
      run: docker build -t ghcr.io/example/shop-api:${{ github.sha }} .
    - name: Scan with Trivy
      uses: aquasecurity/trivy-action@master
      with:
        image-ref: ghcr.io/example/shop-api:${{ github.sha }}
        exit-code: "1"
        severity: HIGH,CRITICAL
    - name: Push
      run: docker push ghcr.io/example/shop-api:${{ github.sha }}

Note the image is tagged with the commit SHA, not a moving tag like latest. Every build is uniquely and immutably identifiable, which is what makes the GitOps half auditable.

The GitOps half

The two dominant GitOps controllers are Argo CD (rich web UI, application-centric, very popular for app teams) and Flux (CNCF-graduated, controller-centric, composes well with other tooling). Both watch a git repo and apply changes; the choice is largely about whether you want a polished UI (Argo CD) or a leaner, more composable toolkit (Flux).

An Argo CD Application pointing at the shop's manifests:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shop
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/example/shop-config
    targetRevision: main
    path: manifests          # where the YAML lives
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true            # delete resources removed from git
      selfHeal: true         # revert manual cluster edits back to git
    syncOptions:
    - CreateNamespace=true

With selfHeal on, if someone runs kubectl edit against production, Argo CD notices the drift from git and reverts it within seconds. The only way to change the cluster is to change git — which means every change is reviewed, attributed, and revertible with git revert.

Why this became the standard

GitOps wins on four counts that matter most in production: a complete audit trail (git history is your change log), trivial rollback (revert the commit), disaster recovery (rebuild a cluster by pointing a fresh controller at the same repo), and least privilege (humans need git access, not cluster credentials — the controller holds those). Combined with the CI scanning step, you get a pipeline where nothing reaches production without passing through review and automated checks.

Separate the code repo from the config repo

A common pattern is two repositories: one for application source (which CI builds) and one for deployment manifests (which the GitOps controller watches). CI's last step bumps the image tag in the config repo, which triggers the deploy. This keeps a fast-moving code history separate from a deliberate, reviewable deployment history — and stops a deploy from accidentally shipping un-built code.
