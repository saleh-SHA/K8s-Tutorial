Chapter 03

Architecture & the control loop

Two kinds of machines, one continuous conversation.

The cluster, top to bottom

A Kubernetes setup is called a cluster. Every cluster has two kinds of machines: a control plane that makes decisions, and worker nodes that run your application containers. On a small learning cluster these can be the same machine, but in production they are usually separate for reliability.

Control plane components

The API server is the front door; every command and every internal communication flows through it. The scheduler decides which worker node a new workload should run on, considering things like available CPU, memory, and constraints you have specified. The controller manager runs the control loops that watch the cluster state and nudge it toward your desired state. And etcd is a distributed key-value store that holds the cluster's entire state. If etcd is lost, the cluster is lost, which is why backing it up matters.

Worker node components

Worker nodes run the kubelet, an agent that talks to the API server and manages the containers on that node, and a container runtime such as containerd that actually starts and stops containers. They also run kube-proxy, which handles network routing for services.

The reconciliation loop

The most important idea in Kubernetes isn't any single component — it's the continuous loop that makes everything else work. Controllers compare desired state (what you declared) to actual state (what's happening) and act to close the gap. This loop runs constantly, for every kind of object.

What actually happens when you run kubectl apply

Tracing a single command through the components turns the architecture from a static diagram into a story you can debug. Suppose you run kubectl apply -f deployment.yaml for the shop's API:

First, kubectl sends the manifest to the API server, which authenticates you, authorises the action against RBAC, runs it through admission controllers (which may mutate or reject it), and — only if all that passes — writes the object to etcd. At this point the Deployment exists but nothing is running. The controller manager is watching; its Deployment controller sees the new object, creates a ReplicaSet, and the ReplicaSet controller creates the required Pod objects — still just records in etcd, unscheduled. The scheduler is watching for unscheduled pods; it picks a suitable node for each and writes that assignment back. Finally the kubelet on the chosen node sees a pod assigned to it, calls the container runtime to pull the image and start the container, and reports status back to the API server. Every step is one component watching the API server and reacting — there is no central orchestrator barking orders, just many control loops reading and writing shared state.

The three interfaces: CRI, CSI, CNI

Kubernetes deliberately does not implement running containers, providing storage, or wiring up networking itself. Instead it defines three pluggable interfaces and lets specialised projects implement them. Knowing these names is essential for real troubleshooting, because when one breaks, the symptom appears in Kubernetes but the fix is in the plugin.

The Container Runtime Interface (CRI) is how the kubelet asks a runtime to pull images and run containers. Implementations include containerd (the common default) and CRI-O. If pods get stuck and node logs mention the runtime, that is a CRI-layer problem.

The Container Storage Interface (CSI) is how Kubernetes provisions and attaches storage. Every cloud disk type, every storage vendor, ships a CSI driver. A PersistentVolumeClaim stuck in Pending is frequently a CSI driver issue, not a Kubernetes one.

The Container Network Interface (CNI) is how pod networking is set up — assigning each pod its IP and wiring up routes. Calico, Cilium, and Flannel are CNI plugins. A pod stuck in ContainerCreating with network errors points at the CNI. We return to CNI choices in the networking chapter.

Three layers of abstraction

A useful mental model is to think of Kubernetes as having three layers. The bottom layer is infrastructure: nodes, the container runtime, networking. The middle layer is workload primitives: pods, deployments, services. The top layer is policy and governance: RBAC, network policies, resource quotas. You will spend most of your time in the middle layer, dipping into the others as you mature.
