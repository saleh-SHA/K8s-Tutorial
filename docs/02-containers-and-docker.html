Chapter 02

Containers & Docker

Kubernetes runs containers. First, get fluent with Docker — the tool you will use to build, run, network, and compose them.

Kubernetes orchestrates containers, so before orchestrating anything you need to be comfortable with the layer beneath it. Docker is the tool most people use to build images and to run containers on a single machine, and almost every concept in Kubernetes is a cluster-scale answer to something Docker does on one host. This chapter is a working tour of Docker — images, the command set, networking, multi-container apps with Compose, and orchestration — framed so that each idea points forward to its Kubernetes counterpart. If you already build and push images daily, skim to the networking, Compose, and orchestration sections. If containers are still fuzzy, this is the foundation everything else rests on.

The journey from source code to a running pod

There is a single pipeline that turns the code on your laptop into a process running inside a Kubernetes cluster. Every stage has a name, and knowing them makes error messages far less mysterious.

Images, containers, and the OCI standard

An image is a read-only, layered filesystem bundled with metadata describing how to run it (the command, environment, exposed ports). A container is a running instance of an image — a normal Linux process, isolated using kernel features (namespaces for what it can see, cgroups for what it can use). The image is the recipe; the container is the meal.

Both are governed by the Open Container Initiative (OCI) specification, which is why an image built with Docker runs identically under containerd, CRI-O, or Podman. Kubernetes does not use Docker to run containers — it talks to an OCI-compliant runtime through the Container Runtime Interface (covered in the architecture chapter). Docker is one way to build images; it is not required to run them.

Why Kubernetes doesn’t use Docker to run containers

This surprises newcomers, especially after Kubernetes “deprecated Docker” made headlines. Kubernetes runs containers through the Container Runtime Interface (CRI), and talks to a CRI-compliant runtime such as containerd or CRI-O — not to the Docker daemon. Because every image is built to the same OCI standard, an image you build with Docker runs perfectly under containerd; nothing about your images or Dockerfiles changes. Docker remains an excellent tool for building images and for local development — it is simply not the component that executes them inside a cluster.

The running example we will build on

Rather than show disconnected snippets, the rest of this tutorial deploys one realistic application — a small online shop — and grows it chapter by chapter. By the end you will have taken it from a Dockerfile to a hardened, observable, autoscaling, GitOps-managed production deployment.

A Dockerfile, and why multi-stage matters

A Dockerfile is the recipe for an image. Here is the backend's, written as a multi-stage build — the single most important image-optimisation technique. The first stage has the full toolchain to install dependencies; the final stage copies only what is needed to run, leaving the build tools behind.

# ---- build stage: has the full toolchain ----
FROM python:3.13-slim AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --prefix=/install -r requirements.txt

# ---- runtime stage: minimal, no build tools ----
FROM python:3.13-slim
WORKDIR /app
# copy only the installed packages and the app code
COPY --from=build /install /usr/local
COPY . .
# run as a non-root user (matches the securityContext we set later)
RUN useradd -u 1000 app && chown -R app /app
USER 1000
EXPOSE 8080
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]

The payoff is real: a naive single-stage Python image can be 1 GB; the multi-stage version is a few hundred megabytes. Smaller images pull faster (shorter pod startup), expose less attack surface, and cost less to store. The same pattern applies to every compiled or bundled language — build in a fat stage, run from a thin one.

Build smaller, safer images

Pin a specific base tag (python:3.13-slim, not python:latest) so builds are reproducible. Add a .dockerignore so secrets, .git, and local junk never enter the image. Prefer slim or distroless bases. Run as a non-root user in the image itself, not just in the Kubernetes manifest — defense in depth.

Building and pushing to a registry

A registry is where images live so that cluster nodes can pull them. Docker Hub is the default public registry; GitHub Container Registry (ghcr.io) is convenient when your code already lives on GitHub and integrates cleanly with GitHub Actions. Cloud providers offer their own (ECR, Artifact Registry, ACR), usually with tighter IAM integration for their managed clusters.

# build, tag for a registry, and push
docker build -t ghcr.io/example/shop-api:1.0.0 .
echo "$GITHUB_TOKEN" | docker login ghcr.io -u USERNAME --password-stdin
docker push ghcr.io/example/shop-api:1.0.0

# the cluster later pulls this exact reference:
#   image: ghcr.io/example/shop-api:1.0.0

The :1.0.0 is the tag. Tags are mutable — someone can re-push :1.0.0 with different contents — which is why production deployments often pin the immutable digest (ghcr.io/example/shop-api@sha256:…) instead. We return to this in the security chapter.

The commands you will actually use

Docker has a large CLI, but day-to-day work runs on a small core. These are the ones worth committing to muscle memory, grouped by what they do. Notice how many have a direct kubectl analogue — that mapping is the fastest way to feel at home in Kubernetes later.

Images

docker build -t shop-api:1.0.0 .        # build an image from the Dockerfile here
docker images                           # list local images
docker pull postgres:17                 # download an image from a registry
docker push ghcr.io/example/shop-api:1.0.0   # upload an image
docker tag shop-api:1.0.0 ghcr.io/example/shop-api:1.0.0   # add a registry tag
docker rmi shop-api:1.0.0               # remove an image
docker history shop-api:1.0.0           # inspect the layers (and their sizes)

Running and managing containers

docker run -d --name api -p 8080:8080 shop-api:1.0.0   # run detached, publish a port
docker run -it ubuntu:24.04 bash        # run interactively with a shell
docker ps                               # list running containers
docker ps -a                            # include stopped containers
docker stop api && docker start api      # stop / start
docker rm api                           # remove a stopped container
docker run --rm alpine echo hi          # auto-remove when it exits

The -p 8080:8080 publishes a container port to the host (HOST:CONTAINER); -d runs in the background; --rm cleans up on exit so you don't accumulate dead containers. In Kubernetes you never type these — a Deployment's spec encodes the same intent declaratively — but understanding them makes the YAML obvious.

Inspecting and debugging — the Docker → kubectl bridge

docker logs -f api                      # stream logs      → kubectl logs -f
docker exec -it api sh                  # shell into it     → kubectl exec -it
docker inspect api                      # full JSON details → kubectl describe
docker stats                            # live CPU/memory   → kubectl top
docker cp api:/app/out.txt .            # copy files out    → kubectl cp

This parallel is not a coincidence. Kubernetes deliberately mirrored the Docker debugging verbs, so the investigative reflexes you build here transfer directly to a cluster.

Housekeeping

docker system df                        # how much disk images/containers/volumes use
docker system prune                     # remove stopped containers, unused networks, dangling images
docker system prune -a --volumes        # aggressive: also unused images and volumes
Disk fills up quietly

Image layers, stopped containers, and orphaned volumes accumulate fast on a development machine. A weekly docker system prune reclaims gigabytes. Be deliberate with -a --volumes — it deletes any image not currently used by a container and any volume not currently mounted, which includes data you may have wanted to keep.

Docker networking

Containers need to talk — to each other and to the outside world — and Docker gives each container its own network namespace, then connects them through networks you can create and manage. Understanding the handful of network types demystifies both Docker and, later, the Kubernetes networking model that generalises them across many machines.

DriverWhat it doesUse it for
bridgeThe default. A private virtual network on the host; containers get internal IPs and reach each other; ports are published to the host with -p.Most single-host setups
hostThe container shares the host's network stack directly — no isolation, no port mapping needed.Maximum performance, rare cases
noneNo networking at all.Fully isolated batch jobs
overlayA network that spans multiple hosts, so containers on different machines communicate as if local.Multi-host clusters (Swarm)

The key practical feature of a user-defined bridge network is automatic DNS: containers on the same network resolve each other by name. Create a network, attach the API and its database to it, and the API reaches the database at the hostname db — no IP addresses, no hardcoding.

# create a network and run two containers on it
docker network create shopnet
docker run -d --name db  --network shopnet postgres:17
docker run -d --name api --network shopnet -p 8080:8080 shop-api:1.0.0

# inside the api container, the database is reachable simply as "db"
docker exec -it api sh -c "ping -c1 db"

docker network ls                       # list networks
docker network inspect shopnet          # see which containers are attached

This name-based discovery is precisely what Kubernetes Services and CoreDNS do at cluster scale: in Kubernetes the API will reach Postgres at the name postgres exactly as it reaches db here. Docker's overlay driver is the same idea stretched across hosts — and it is the direct ancestor of the pod network in a multi-node cluster.

Persisting data with volumes

A container's filesystem is ephemeral: delete the container and its writes are gone. Volumes are Docker's mechanism for data that must outlive a container — exactly the problem PersistentVolumes solve in Kubernetes.

docker volume create pgdata
docker run -d --name db --network shopnet \
  -v pgdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret postgres:17

docker volume ls                        # list volumes
docker volume inspect pgdata            # where/what it is

A named volume (pgdata) is managed by Docker and survives container removal; a bind mount (-v $(pwd)/code:/app) maps a host directory into the container, which is invaluable in development for live-reloading source code. The -e flag sets an environment variable — the single-container ancestor of ConfigMaps and Secrets.

Docker Compose: many containers, one file

Running the shop by hand means several docker run commands in the right order with matching network and volume flags — tedious and error-prone. Docker Compose replaces all of that with a single declarative compose.yaml describing every service, and brings the whole stack up or down with one command. It is the natural bridge between single docker run commands and Kubernetes manifests: same declarative spirit, single-host scope.

# compose.yaml — the whole shop on one machine
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: shop
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: shop
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "shop"]
      interval: 5s

  cache:
    image: redis:7

  api:
    build: ./api                 # build from a local Dockerfile
    ports:
      - "8080:8080"
    environment:
      DATABASE_HOST: db          # reach other services by name
      REDIS_HOST: cache
    depends_on:
      db:
        condition: service_healthy

volumes:
  pgdata:
docker compose up -d            # build (if needed) and start everything
docker compose ps               # what's running
docker compose logs -f api      # follow one service's logs
docker compose down             # stop and remove containers + networks
docker compose down -v          # also delete named volumes

Compose automatically creates a network for the project, so db, cache, and api find each other by name — the same discovery pattern again.

Docker → Kubernetes: a concept map

Almost every Docker idea has a direct Kubernetes counterpart. If you are comfortable with the left column, you already have a foothold in the right one — the rest of this tutorial is largely about what each Kubernetes concept adds once you are running across many machines rather than one.

Docker conceptKubernetes equivalentWhat changes at cluster scale
ImageImageIdentical — the same OCI image runs in both
ContainerContainer (inside a Pod)Wrapped in a pod, the smallest deployable unit
docker runPod (usually via a Deployment)Scheduled onto a node automatically; recreated if it dies
Compose serviceDeploymentDeclarative replicas, rolling updates, self-healing
Docker network / DNSService + CNICluster-wide discovery across every node
VolumePersistentVolumeClaimStorage that can follow a pod across nodes
Environment variablesConfigMap / SecretCentralised, versioned, separately access-controlled
HealthcheckLiveness / readiness probeDrives restarts and traffic routing automatically

From Compose to Kubernetes

This is the key transition to internalise. Compose solves multi-container deployment on a single machine: it starts your services in the right order, wires them onto one network, and tears them down together. Kubernetes solves those same problems across many machines — and that distribution is precisely why it needs more moving parts. A Compose service bundles together concerns that Kubernetes deliberately separates into independent, individually scalable resources.

Read the diagram as a promotion, not a complication: the container image and its intent are unchanged, but each concern Compose kept implicit (how many copies, how they are reached, where config and secrets come from, how data persists) becomes an explicit Kubernetes object you can scale, secure, and update on its own. Learning Compose first makes the end-to-end manifests later in this tutorial feel familiar rather than foreign.

A note on Docker Swarm

Docker has its own built-in orchestrator, Swarm (docker swarm init, then docker service create --replicas 3), which turns a group of Docker hosts into a single cluster. It is historically important and genuinely simple — if you know Compose, you nearly know Swarm. In practice, though, the ecosystem has moved on: Kubernetes became the dominant orchestrator thanks to its vast extension ecosystem, its extensibility (custom resources and operators), and near-universal cloud-provider adoption (EKS, GKE, AKS). Swarm still works for small setups, but new projects and the surrounding tooling overwhelmingly target Kubernetes, which is why the rest of this tutorial does too.

The handoff: Docker vs Kubernetes

Docker gets containers running on a machine. Kubernetes is what you add when “a machine” becomes “a fleet” and the work has to keep running without you watching it.

CapabilityDocker / Compose (one host)Kubernetes (many hosts)
Self-healingManual restart; restart: policy per hostAutomatic — failed pods recreated, bad nodes drained
Scaling across machinesLimited to the one hostSchedules replicas across the whole cluster
Rolling updatesNot built inBuilt in, with health-gated rollout and rollback
Service discoveryPer-host DNS on a Docker networkCluster-wide DNS via Services and CoreDNS
AutoscalingNoneHorizontal, vertical, and event-driven (HPA / VPA / KEDA)

Docker teaches you how to run containers. Kubernetes teaches you how to run thousands of them reliably.
