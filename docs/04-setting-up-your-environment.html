Chapter 04

Setting up your environment

A real cluster in one command.

What you need

You need two tools on your Linux machine before anything else: kubectl, the command-line client for talking to a cluster, and a cluster to talk to. For learning, the easiest cluster is a local one using minikube, kind, or k3s. For a real deployment server, you will typically use a managed service such as Amazon EKS, Google GKE, or Azure AKS, or you will install Kubernetes yourself on Linux servers using kubeadm or a distribution like k3s.

Installing kubectl

On Ubuntu or Debian:

curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
kubectl version --client

Local learning cluster with minikube

curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube
minikube start --driver=docker
kubectl get nodes

Local multi-node cluster with Kind

Kind (Kubernetes IN Docker) runs each node as a Docker container, which makes it fast to create and tear down and trivial to spin up a multi-node cluster on a single machine. It is the tool most Kubernetes contributors and CI pipelines use, because a config file gives reproducible clusters in seconds.

# install
go install sigs.k8s.io/kind@latest    # or: brew install kind

# a 3-node cluster (1 control-plane, 2 workers) from a config file
cat > kind-config.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
- role: worker
EOF
kind create cluster --config kind-config.yaml
kubectl get nodes

Because Kind clusters are disposable and config-driven, they are ideal for testing things that need more than one node — pod anti-affinity, topology spread, DaemonSets, rolling updates across nodes — which a single-node minikube cannot demonstrate.

Production single-server cluster with k3s

For a real single-server deployment, k3s is an excellent lightweight option. It installs a production-grade Kubernetes cluster in a single command:

curl -sfL https://get.k3s.io | sh -
sudo k3s kubectl get nodes

After installing, copy the kubeconfig file to your user's home directory so plain kubectl works:

mkdir -p ~/.kube
sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown $(id -u):$(id -g) ~/.kube/config

Which cluster should you use?

The right choice depends entirely on what you are doing. Local tools are for learning and development; managed services are for production unless you have a strong reason to run the control plane yourself.

OptionBest forStrengthsTrade-offs
minikubeFirst steps, single-node learningSimple, addons (dashboard, metrics-server), VM or Docker driverSingle node by default; not representative of production
KindLocal multi-node, CI pipelinesFast, disposable, reproducible from config, easy multi-nodeNodes are containers, not VMs; not for production
k3sEdge, IoT, small production, homelabProduction-grade in one command, tiny footprint, can run real workloadsYou operate it yourself; some defaults differ from upstream
EKS / GKE / AKSProduction on a cloudManaged control plane, autoscaling, cloud-integrated storage/LB/IAMCost; provider lock-in; you still own the workloads and worker nodes
kubeadmSelf-managed production on your own serversFull control, no provider dependency, upstream KubernetesYou own everything: upgrades, etcd backups, HA control plane

A common path is to learn on minikube or Kind, prototype real deployments on k3s, and run production on a managed service so that the control plane, etcd backups, and node autoscaling are someone else's responsibility.

Verifying the cluster

kubectl get nodes
kubectl get pods --all-namespaces

You should see at least one node in Ready state and a handful of system pods in the kube-system namespace. If both are healthy, you have a working Kubernetes cluster.

On versions

The Kubernetes project only maintains the three most recent minor versions at any time — as of this writing that is the 1.34–1.36 range, with 1.36 being the latest. Each minor release gets roughly a year of patches. Start new clusters on a current version and plan to upgrade about once a year; running an unsupported version means no security fixes, which becomes a liability faster than most teams expect.

Watch out

kubectl uses contexts to switch between clusters. kubectl config get-contexts lists them; kubectl config use-context <name> switches between them. Get into the habit of checking which context you are pointed at before running destructive commands. A casual kubectl delete against the wrong cluster has ruined many afternoons.
