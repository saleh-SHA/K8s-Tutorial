Chapter 05

Pods, deployments & the workload hierarchy

Three objects, one carefully designed indirection.

Time to deploy the first piece of the shop. Its frontend is stateless and horizontally scalable — the textbook case for a Deployment — so we start there. (We use an nginx image as a stand-in for the built React frontend; the shape of the manifest is identical either way.)

The hierarchy

A Pod is the smallest deployable unit. It wraps one or more containers that share networking and storage. Most pods contain a single container, but tightly coupled helpers (sometimes called sidecars) can live alongside it. Pods are intentionally ephemeral. You rarely create one directly.

Instead, you create a Deployment, which describes a desired number of identical pod replicas and manages rolling updates between versions. The Deployment owns a ReplicaSet, which in turn owns the pods. When you update a Deployment's image, it creates a new ReplicaSet, gradually scales it up, and scales the old one down.

Writing your first Deployment

Create a file called web-deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.29
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: "100m"
            memory: "64Mi"
          limits:
            cpu: "500m"
            memory: "128Mi"

Reading the manifest

The apiVersion and kind together tell Kubernetes what type of object this is. The metadata gives it a name and labels. Labels are arbitrary key-value tags that let other objects find and group resources; here the label app: web will be how a Service finds these pods later.

Under spec, replicas: 3 declares that you want three running copies. The selector tells the Deployment which pods it owns, and it must match the labels in the template below it. The template is the recipe for each pod.

Requests vs limits

The resources block is one of the most consequential settings you will write. Requests are what Kubernetes guarantees and uses for scheduling; if a pod requests 100m CPU (a tenth of a core) and 64Mi of memory, the scheduler will only place it on a node with that much free. Limits are the maximum the container can use; exceeding the memory limit gets the container killed, exceeding the CPU limit throttles it. Setting both is one of the simplest things you can do to make a cluster reliable.

Applying and observing

kubectl apply -f web-deployment.yaml
kubectl get pods -l app=web --watch

After a few seconds you should see three pods in Running state. Now try the magic trick that makes Kubernetes feel real:

kubectl delete pod <pod-name>

Then list the pods again. A new one will already be starting. The Deployment noticed the count dropped to two, and a controller created a replacement to bring it back to three. This is the reconciliation loop in action.

Scaling and updating

kubectl scale deployment web --replicas=5
kubectl set image deployment/web web=nginx:1.29.1
kubectl rollout status deployment/web
