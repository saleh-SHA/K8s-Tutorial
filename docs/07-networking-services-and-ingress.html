Chapter 07

Networking, services & ingress

From ephemeral pod IPs to a stable public URL.

The problem with pod IPs

The pods you just created have IP addresses inside the cluster, but those addresses change every time a pod is replaced. You need a stable way to reach them.

Services and label selectors

A Service provides a single DNS name and IP that load-balances across whichever pods currently match its selector. Pods come and go; the Service quietly updates its list of endpoints.

A minimal Service

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
  type: ClusterIP

Any pod in the cluster can now reach the web pods through this Service's IP, or through the DNS name web.default.svc.cluster.local (or just web from within the same namespace).

CoreDNS and service discovery

That DNS name is not magic — it is served by CoreDNS, a DNS server that runs as pods inside the cluster (you can see it with kubectl get pods -n kube-system -l k8s-app=kube-dns). Every Service automatically gets a DNS record of the form <service>.<namespace>.svc.cluster.local, and every pod's /etc/resolv.conf is configured to ask CoreDNS first.

Search domains mean you rarely type the full name. From a pod in the shop namespace, the API reaches the database as just postgres; from another namespace it would use postgres.shop; the fully qualified postgres.shop.svc.cluster.local always works. This is how the shop's FastAPI backend finds Postgres and Redis without anyone hardcoding an IP: it connects to the names postgres and redis, and CoreDNS resolves them to the current Service IPs. When service-to-service calls fail, DNS is the first thing to check — exec into a pod and run nslookup postgres before suspecting anything more exotic.

CNI: the plugin that gives pods their network

Pod-to-pod networking — the flat space where any pod can reach any other pod by IP — is not built into Kubernetes. It is implemented by a CNI plugin (Container Network Interface), chosen when the cluster is created. You usually do not interact with it directly, but the choice determines performance, whether NetworkPolicies are enforced, and what observability you get. The common options:

CNIApproachNotes
FlannelSimple VXLAN overlayEasy to run; no NetworkPolicy enforcement on its own. k3s default.
CalicoRouting (optionally overlay) + rich policyThe classic choice for NetworkPolicy enforcement at scale.
CiliumeBPF in the kernelFastest at scale, deep observability, can replace kube-proxy. The direction most new self-hosted clusters take.
Weave NetOverlay (legacy)Once popular, now effectively unmaintained — avoid for new clusters.

The practical upshot: if you intend to use NetworkPolicies (and in production you should), pick a CNI that enforces them — Calico or Cilium. Managed clusters usually default to one that does.

The four Service types

ClusterIP is internal only and is the default. NodePort opens a high-numbered port on every node, useful for development. LoadBalancer asks your cloud provider for an external load balancer; on bare metal you can get equivalent behavior with MetalLB. ExternalName is a DNS-only alias for routing to services outside the cluster.

Ingress for HTTP and HTTPS

For real production HTTP traffic you almost always want an Ingress, which handles hostnames, URL paths, and TLS termination from a single external entrypoint, rather than paying for one cloud load balancer per Service. An Ingress object is just routing rules; the actual work is done by an Ingress Controller running in the cluster. Common maintained choices are Traefik (which ships with k3s and is the default in the example below), HAProxy, and Envoy-based controllers such as Envoy Gateway and Contour.

Important — ingress-nginx is retired

The community ingress-nginx controller — historically the most widely deployed Ingress controller, and the one most older tutorials default to — was retired by Kubernetes SIG Network in March 2026. Its repositories are archived and it receives no further releases, bug fixes, or security patches. Existing installs keep routing traffic, but running an unmaintained, internet-facing component accumulates security risk, so it should not be chosen for new clusters.

If you have inherited a cluster using it, plan a migration. The recommended long-term destination is the Gateway API (see below); maintained drop-in-ish Ingress controllers such as Traefik, HAProxy, and F5's NGINX Ingress Controller (a separate, actively maintained project, not the retired one) are reasonable interim targets.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: traefik
  tls:
  - hosts:
    - example.com
    secretName: example-com-tls
  rules:
  - host: example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web
            port:
              number: 80

Combined with cert-manager (which automates Let's Encrypt certificates), this gives you HTTPS termination, certificate renewal, and host-based routing in a few lines of YAML. Set ingressClassName to whatever controller you actually run — traefik on a default k3s cluster, or the class your chosen controller registers.

The Gateway API: where Ingress is heading

The Ingress API was designed in 2015 and is now effectively feature-frozen — most advanced behaviour lives in controller-specific annotations that do not port between controllers. Its successor, the Gateway API, has been generally available since 2023 and is the direction the ecosystem is consolidating on. It splits routing into role-oriented resources — GatewayClass and Gateway (owned by cluster operators) and HTTPRoute (owned by application teams) — and supports richer matching and multiple protocols without annotations. Most modern controllers (Traefik, Cilium, Istio, Envoy Gateway, Contour) implement it. Ingress still works and will for years, but if you are starting fresh, it is worth evaluating Gateway API from day one.

When to reach for a service mesh

Everything above handles connectivity. A service mesh adds a layer of control and visibility between services without changing application code, typically by injecting a small proxy alongside each pod (a sidecar) or running in the kernel via eBPF. The headline features: automatic mutual TLS so all service-to-service traffic is encrypted and authenticated, fine-grained traffic management (canary releases, retries, timeouts, circuit breaking), and detailed telemetry for every call between services.

The main options are Istio (the most feature-rich, Envoy-based, now with a lighter sidecar-free "ambient" mode), Linkerd (deliberately simple and lightweight, easy to adopt), and Cilium Service Mesh (eBPF-based, no sidecars, natural if you already run Cilium as your CNI).

A mesh is not free — it adds operational complexity and some latency — so it earns its place only once you have enough services that manual TLS, per-service retry logic, and cross-service tracing become genuinely painful. For the shop's four components it would be overkill; for a few dozen microservices it starts to pay off. Treat it as something to grow into, not a starting requirement.
